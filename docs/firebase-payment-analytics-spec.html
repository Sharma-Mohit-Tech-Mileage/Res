Firebase Payment Analytics — Tracking Specification

Deliverable for 53800 · input to 53472 · Residential & Business mobile apps

Scope: Make a Payment, Manage Payment Methods, Manage AutoPay.
Goal: measure funnel drop-off, reconstruct individual payment journeys, and detect when customers get stuck or hit errors — without sending personal data to Firebase.

1. Current state

Both apps today emit 8 event names and 1 user property:

EventsUser property
screen_view, business_screen_view, login, Zendesk_Chat_Start, feature_announcement_impression, feature_announcement_step_viewed, feature_announcement_completed, feature_announcement_dismissed Sparklight_user_id (set to the account number)

No payment analytics exist. Everything in this document is new.

Two existing capabilities matter:

  • screen_view fires automatically on every navigation (UserNavigations.js), carrying screen_name.
  • Firebase attaches ga_session_id and ga_session_number to every event automatically.

The payment flow is a linear chain of uniquely-named routes — MakePayment → MakePaymentMethod → MakePaymentReview → PaymentConfirmation — so step-by-step drop-off is already measurable today with no new code.

2. Impact on existing analytics

Adding these events has no impact on existing analytics. The change is additive only.
ConcernAssessment
Name collisionsNone. All 14 new names are distinct from the 8 in use.
Reserved namesNone. No use of the reserved firebase_, google_ or ga_ prefixes.
Firebase event-name limit (500/app)8 → 22. Well within.
Parameter limit (25/event)Maximum 4 parameters on any event proposed here.
Existing events & dashboardsUntouched. screen_view, login and the announcement events keep firing exactly as now.
Historical dataUnaffected. No retroactive change.
App performance / payment processingNo impact — calls are fire-and-forget and wrapped in try/catch.
One exception, and it needs Analytics sign-off. The privacy recommendation in §6 is to stop sending the account number as the user identifier. If setUserId / Sparklight_user_id is changed or removed, any existing user-scoped report or audience built on it will lose continuity — historical data remains, but new data will no longer join to it. This is the only proposed change that touches existing analytics, and it should be agreed with the Analytics team before implementation, not after.

3. Two approaches

Events2114
ProsMatches 53472 exactly. No negotiation with Analytics.Every event carries information not otherwise obtainable. Half the call sites to keep in sync across two apps. Abandonment computed correctly instead of guessed.
ConsFour events duplicate screen_view (payment_flow_started, payment_reviewed, payment_method_viewed, autopay_viewed). 42 call sites across both apps. payment_flow_abandoned cannot be fired reliably — app kill, backgrounding and navigation-away are indistinguishable.Funnel steps come from screen_view, so dashboards must be pointed there. Recommendation: Approach B. Screens answer where customers drop. Events should answer what they chose, what happened, and what broke. An event that restates a screen adds volume and drift risk without answering a new question.

4. Session & journey model

IdentifierSourcePurpose
ga_session_idFirebase, automaticGroups all events in one app session (30-min inactivity window).
payment_attempt_idNew. Random UUID generated on entering a flow, discarded on exit or completion.Groups one attempt. Distinguishes two failed tries and a success within a single session, which ga_session_id alone cannot.

Attach payment_attempt_id to every payment event; ordering by timestamp within it reconstructs the journey. Satisfies AC4, AC5 and AC6 of 53800 with one parameter and no personal data.

Health — detecting stuck and broken journeys

EventFires whenParameters

A drop in payment_success reveals a problem days later. payment_api_error names the endpoint, status and step within minutes. payment_step_duration surfaces friction no funnel count shows — a step whose median time doubles after a release is a defect.

6. Privacy

Never send: account number, email address, card last-four, cardholder name, confirmation number, exact payment amount.

Amounts are sent as amount_bucket — 0-50, 50-100, 100-250, 250+. Reporting needs the distribution, not a financial record per customer.

Pre-existing issue. SplashScreen.js sends the account number to Firebase three ways: setUserId(accountNumber), setUserProperty("Sparklight_user_id", …), and as a login event parameter. Adding payment events makes that identifier joinable to payment behaviour and amounts. Recommend hashing it, or removing it and relying on payment_attempt_id plus Firebase's own instance id. See §2 for the impact of changing it.

7. Dashboard views enabled

  • Funnel — screen_view counts per step, grouped by ga_session_id.
  • Abandonment — sessions with MakePayment but no payment_success. Derived, so correct by construction.
  • Conversion by choice — success rate split by payment_type and payment_method_type.
  • Failure breakdown — payment_failed by failure_reason; payment_api_error by endpoint and status.
  • Friction — median payment_step_duration per step, tracked across releases.
  • Journey replay — all events for one payment_attempt_id in timestamp order.

8. Implementation notes

  • One shared helper per app (paymentAnalytics.js), identical in both repos, so Residential and Business cannot drift. All events route through it.
  • Every call wrapped in try/catch and never awaited in a user-blocking path.
  • Naming: snake_case throughout. Existing Zendesk_Chat_Start and Business-only business_screen_view break this convention; worth aligning separately.
  • Parameter sources already in code: amountOption → payment_type; method.type → payment_method_type; method.cardType → card_type.
  • Validate in Firebase DebugView on both apps before release.
