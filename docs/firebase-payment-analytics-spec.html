Firebase Payment Analytics — Tracking Specification

Deliverable for 53800 · input to 53472 · Residential & Business mobile apps

Scope: Make a Payment, Manage Payment Methods, Manage AutoPay.
Goal: measure funnel drop-off, reconstruct individual payment journeys, and detect when customers get stuck or hit errors — without sending personal data to Firebase.

1. Current state

Both apps today emit 8 event names and 1 user property:

EventsUser property
screen_view, business_screen_view, login, Zendesk_Chat_Start, feature_announcement_impression, feature_announcement_step_viewed, feature_announcement_completed, feature_announcement_dismissed Sparklight_user_id (set to the account number)

No payment analytics exist. Everything in this document is new.

  • screen_view fires automatically on every navigation (UserNavigations.js), carrying screen_name.
  • ga_session_id and ga_session_number are attached by Firebase to every event automatically.

The payment flow is a linear chain of uniquely-named routes — MakePayment → MakePaymentMethod → MakePaymentReview → PaymentConfirmation — so step-by-step drop-off is already measurable today with no new code.

3. Approach

Funnel steps come from the existing screen_view. Custom events are added only where they carry information a screen cannot.

A screen tells you where a customer was. It cannot tell you what they chose or what happened — for example, success and failure both land on PaymentConfirmation, so screen_view records them identically. Custom events fill exactly that gap.

Applying that rule, seven events from 53472 are not implemented because screen_view already records the same fact:

Excluded eventReason
payment_flow_startedDuplicate of screen_view: MakePayment
payment_reviewedDuplicate of screen_view: MakePaymentReview
payment_method_viewedDuplicate of screen_view: PaymentMethods
autopay_viewedDuplicate of screen_view: AutoPay
payment_amount_selectedRenamed to payment_type_selected for consistency
payment_method_updated, payment_method_default_changedNot supported by the current app — no update or default-selection flow exists
payment_flow_abandonedCannot be fired reliably — app kill, backgrounding and navigation-away are indistinguishable. Derived instead (see §8).
Emitting an event that restates a screen means two systems reporting the same fact, kept in sync across two apps forever. They drift the first time someone adds a screen and updates only one.

4. Session & journey model

IdentifierSourcePurpose
ga_session_idFirebase, automaticGroups all events in one app session (30-min inactivity window).
payment_attempt_idNew. Random UUID generated on entering a flow, discarded on exit or completion.Groups one attempt. Distinguishes two failed tries and a success within a single session, which ga_session_id alone cannot.

Attach payment_attempt_id to every payment event; ordering by timestamp within it reconstructs the journey. It identifies an attempt, not a person — no personal data is involved. Satisfies AC4, AC5 and AC6 of 53800.

A drop in payment_success reveals a problem days later. payment_api_error names the endpoint, status and step within minutes. payment_step_duration surfaces friction no funnel count shows — a step whose median time doubles after a release is a defect.

6. Privacy & customer identifier

Never send: account number, email address, card last-four, cardholder name, confirmation number, exact payment amount.

Amounts are sent as amount_bucket — 0-50, 50-100, 100-250, 250+. Reporting needs the distribution, not a financial record per customer.

Identifier — retained, with reset gaps to close

SplashScreen.js sends the account number to Firebase three ways: setUserId(accountNumber), setUserProperty("Sparklight_user_id", …), and as a login event parameter. The decision is to retain this — it preserves reporting continuity and avoids repointing existing audiences.

Two controls keep that acceptable, and both are already in this spec: amounts are bucketed rather than exact, and no new identifier is added to any payment event.

The remaining requirement is that the identifier is reliably cleared when a session ends. It currently is not:

Exit pathClears identifier?
Logout via Account screenYes — setUserId(null) + property null
Logout via SplashScreen.logoutActionYes — resetAnalyticsData()
GlobalErrorModal closeYes — Business only; missing in Residential
RestApiClient.redirectToLogin() — 401 refresh failureNo
MaintenanceContext.performLogout()No
Why this matters once payment events exist. The two paths that do not clear leave the identifier pointing at the previous account. Any event fired before the next login is attributed to the wrong customer — with payment events, that means a payment journey recorded against someone who did not make it. The token-expiry failures that trigger redirectToLogin() are known to occur in production.

Fix: add the reset to redirectToLogin() and MaintenanceContext.performLogout() in both apps, and add the missing GlobalErrorModal reset in Residential. Roughly ten lines per app. This is a defect in existing behaviour rather than new scope.

7. How to view the data

A. During development and QA — DebugView (real time)

DebugView shows events from a single device within seconds. This is how QA validates the implementation.

  1. Enable debug mode on the test device:
    • Android — adb shell setprop debug.firebase.analytics.app com.sparklight (Residential) or com.sparklight.customer.business.app (Business)
    • iOS — add the launch argument -FIRDebugEnabled in the Xcode scheme
  2. Firebase Console → select the project → Analytics → DebugView
  3. Select the device in the top-left dropdown
  4. Walk the payment flow — events appear in a live timeline, and clicking one shows its parameters

Turn debug mode off afterwards (adb shell setprop debug.firebase.analytics.app .none.), or that device's data stays excluded from normal reporting.

B. In reporting — Firebase Console (24-hour delay)

  • Analytics → Events — count per event name, per day. Confirms events are arriving in volume.
  • Analytics → Explore → Funnel exploration — build the drop-off funnel. Use screen_view with screen_name as each step: MakePayment → MakePaymentMethod → MakePaymentReview → PaymentConfirmation.
  • Analytics → Explore → Free form — cross-tabulate, e.g. payment_failed broken down by failure_reason.
Required setup — parameters are not reportable until registered. Firebase collects custom parameters immediately, but they will not appear in Console reports until each one is registered as a custom definition. Without this step the events show up with no usable breakdowns, which reads like a broken implementation.

Go to Analytics → Custom definitions → Create custom dimension and register each parameter, event-scoped:

payment_type, payment_method_type, card_type, amount_bucket, failure_reason, entry_point, payment_attempt_id, endpoint, status, step, field, reason, seconds

13 dimensions against a limit of 50. Data only becomes available from the moment of registration — it is not backfilled, so register these before release.

C. Journey replay — BigQuery

Console reports are aggregated. To see one customer's exact sequence — the AC5 requirement — you need event-level rows, which means the BigQuery export.

  1. Firebase Console → Project settings → Integrations → BigQuery → link, and enable the daily export for both apps.
  2. Query a single attempt:
SELECT event_timestamp, event_name,
       (SELECT value.string_value FROM UNNEST(event_params)
        WHERE key = 'payment_attempt_id') AS attempt_id
FROM `<project>.analytics_<id>.events_*`
WHERE event_name LIKE 'payment%'
ORDER BY event_timestamp

Export begins from the day it is linked; there is no historical backfill.

8. Dashboard views enabled

  • Funnel — screen_view counts per step, grouped by ga_session_id.
  • Abandonment — sessions with MakePayment but no payment_success. Derived, so correct by construction.
  • Conversion by choice — success rate split by payment_type and payment_method_type.
  • Failure breakdown — payment_failed by failure_reason; payment_api_error by endpoint and status.
  • Friction — median payment_step_duration per step, tracked across releases.
  • Journey replay — all events for one payment_attempt_id in timestamp order (BigQuery).

9. Implementation notes

  • One shared helper per app (paymentAnalytics.js), identical in both repos, so Residential and Business cannot drift. All events route through it.
  • Every call wrapped in try/catch and never awaited in a user-blocking path.
  • Naming: snake_case throughout. Existing Zendesk_Chat_Start and Business-only business_screen_view break this convention; worth aligning separately.
  • Parameter sources already in code: amountOption → payment_type; method.type → payment_method_type; method.cardType → card_type.
  • Validate in Firebase DebugView on both apps before release.
