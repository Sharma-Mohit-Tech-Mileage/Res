Pipeline Overview

What the repo actually does

The main Azure pipeline starts with an initial commit validation stage, then splits into Android and iOS build paths. After build, the pipeline runs unit tests, lint and security checks, code review gates, and then platform-specific release steps.

Android ends with a Google Play internal testing release. iOS ends with IPA staging validation and a TestFlight upload when the branch and parameter conditions match the values in the YAML.

Simple flow summary
  • Commit or PR triggers the pipeline.
  • InitialCommit validates branch and commit context.
  • Android and iOS build jobs run in their own paths.
  • Tests, lint, and security checks run before release.
  • Artifacts are published for Android AAB and iOS IPA.

Build Process

Android build

The main pipeline installs JDK 17, installs Node 20.6.1, cleans npm cache, runs npm install --legacy-peer-deps, downloads the Android keystore, validates the SHA1 fingerprint, and runs clean bundleDemoRelease in Gradle.

The Android Gradle file shows product flavors Dev, Demo, and Prod, with the main pipeline building the DemoRelease variant.

iOS build

The iOS path selects the installed Xcode version, installs Node, runs pod install, patches the code signing identity, installs the certificate and provisioning profile, disables Pods code signing, sets the build number, and archives/exports an IPA.

The YAML contains explicit release and signing variables such as team ID, bundle ID, provisioning profile, and API key identifiers.

Lint Usage

What lint does here

Linting checks code quality, formatting, syntax, and maintainability before release. The ESLint configuration also restricts raw React Native touchable imports outside the shared Touchable.js primitive.

That guardrail helps enforce a consistent accessibility pattern for interactive elements.

Actual lint commands found
  • npx eslint src/ --ext .js,.jsx,.ts,.tsx --format json --output-file eslint-report.json
  • npx prettier --check src/ 2>&1 | tee prettier-report.txt
  • cd android && ./gradlew lintDemoRelease --no-daemon

Unit Test Cases using Jest / JTest

What the tests are for

The repository uses Jest to validate screen behavior, hooks, reducers, helper functions, and navigation flows before build or deployment. The repo does not show a separate JTest tool; the actual tool present is Jest, with jest-junit used for CI test reporting.

The main pipeline runs Jest with coverage, and the iOS path runs Jest with --runInBand and coverage as well.

Artifact Generation

Android artifacts

Android build outputs are published from android/app/build/outputs after the AAB build completes.

iOS artifacts

The iOS pipeline publishes the exported IPA from the build artifact staging directory.

Reports

Jest coverage, lint reports, and security reports are staged and published as pipeline artifacts.

Deployment / Release Flow

Android release

The internal testing deployment stage downloads the Android artifact, resolves the AAB path, generates release notes, and uploads the bundle to Google Play internal testing using GooglePlayRelease@4.

An email notification step is present if SMTP variables are configured in Azure DevOps.

iOS release

The iOS staging stage validates the IPA, then the TestFlight stage uploads the IPA with xcrun altool using an App Store Connect API key. A notification email step is also present if SMTP variables exist.

Benefits of Pipeline

Automation

Builds, tests, linting, and artifact publication happen the same way every time.

Early detection

Coverage gates, lint rules, and security checks catch issues before release.

Consistency

Android and iOS use explicit versions, signing inputs, and repeatable commands.

Faster release

Artifacts are ready for internal testing or TestFlight without manual rebuild steps.
